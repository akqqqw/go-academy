# Запуск пользовательского Go-кода

Два режима работы, между которыми переключает **одна переменная окружения**:

| Режим | Когда | Изоляция |
| --- | --- | --- |
| `CODE_RUNNER_URL` задан | продакшн | отдельный сервис `coderunner` в контейнере: без базы, без секретов API, без выхода в интернет, с лимитами CPU/RAM/времени |
| переменная пуста | локальная разработка | тот же процесс, что и API: лимиты есть, песочницы нет — интерфейс показывает предупреждение |

Контракт клиентов (`/api/editor/*`, `/api/exercises/{id}/submit`) в обоих режимах
одинаков: web и мобильное приложение не знают, где выполняется код.

```text
Web / Mobile
   │  POST /api/editor/run (JWT Supabase)
   ▼
Go-API (Vercel) ──HTTP+Bearer──► coderunner (контейнер: --network=runner-net --internal, --read-only)
   │                                   │
   ▼                                   ▼
Supabase Postgres                 go build → go run внутри контейнера
```

## 1. Как это устроено в коде

| Файл | Роль |
| --- | --- |
| `backend/internal/runner/executor.go` | интерфейс `Executor`: `Run`, `Build`, `Format`, `Test`, `Status` |
| `backend/internal/runner/runner.go` | локальный исполнитель: `go build`, запуск бинарника, `gofmt` |
| `backend/internal/runner/grade.go` | проверка задания через `go test -json` |
| `backend/internal/runner/remote.go` | клиент сервиса (`RemoteRunner`), протокол `WireRequest`/`WireFormatResponse` |
| `backend/cmd/coderunner/main.go` | сам сервис: `POST /run`, `/build`, `/format`, `/test`, `GET /status`, `/healthz` |
| `backend/deploy/coderunner/Dockerfile` | образ с Go-тулчейном, непривилегированный пользователь, healthcheck |
| `backend/internal/api/api.go` | выбор исполнителя по `CODE_RUNNER_URL` (`newRunner`) |

`api.Server` держит поле типа `runner.Executor`, поэтому добавление третьего
варианта (например, gVisor или Firecracker) не требует правок обработчиков.

## 2. Лимиты

| Ограничение | По умолчанию | Где задаётся |
| --- | --- | --- |
| время выполнения | 10 с | `CODERUNNER_TIMEOUT_SEC` (1–60) |
| время сборки | 40 с | константа раннера |
| ожидание свободного слота | 15 с | константа раннера |
| размер исходника | 256 КиБ | `CODERUNNER_MAX_CODE` |
| размер вывода | 256 КиБ на поток | `CODERUNNER_MAX_OUTPUT` |
| одновременных запусков | 2 | `CODERUNNER_CONCURRENCY` |
| CPU / RAM / pids контейнера | 1 CPU / 512 МБ / 128 | флаги `docker run` |
| сеть | без выхода в интернет | `docker network create --internal runner-net` |
| файловая система | read-only + tmpfs `/tmp` | `--read-only --tmpfs /tmp:rw,size=256m` |
| права | непривилегированный `10001` | `USER 10001` в Dockerfile |

Проверки до запуска: пустой исходник, превышение размера, отклонение опасных
конструкций (`os/exec`, `syscall`, работа с сетью) — последнее делает сам раннер
и возвращает статус `rejected` с объяснением.

## 3. Сборка и запуск сервиса

```bash
cd backend
docker build -f deploy/coderunner/Dockerfile -t go-academy/coderunner .

# внутренняя сеть без шлюза: у кода нет выхода в интернет
docker network create --internal runner-net

docker run --rm --name coderunner --network runner-net \
  --read-only --tmpfs /tmp:rw,nosuid,size=256m \
  --cpus=1 --memory=512m --memory-swap=512m --pids-limit=128 \
  --cap-drop=ALL --security-opt=no-new-privileges \
  -e CODERUNNER_TOKEN="$(openssl rand -hex 32)" \
  -e CODERUNNER_CONCURRENCY=2 \
  go-academy/coderunner
```

Порт `8090` наружу не публикуется: API обращается к сервису по внутренней сети
(`CODE_RUNNER_URL=http://coderunner:8090`). Сеть `--internal` не имеет внешнего
шлюза, поэтому ни сервис, ни компилируемый в нём код не могут выйти в интернет.
Для ужесточения добавьте `--runtime=runsc` (gVisor). Проверка живости — из
контейнера API или через `docker exec`:

```bash
docker exec coderunner wget -qO- http://127.0.0.1:8090/healthz   # {"status":"ok"}
docker exec coderunner wget -qO- --header="Authorization: Bearer $TOKEN" \
  http://127.0.0.1:8090/status
```

## 4. Подключение к API

| Переменная | Значение |
| --- | --- |
| `CODE_RUNNER_URL` | адрес сервиса, например `http://coderunner:8090` |
| `CODE_RUNNER_TOKEN` | тот же секрет, что `CODERUNNER_TOKEN` |

Старт API проверяет обе переменные: адрес без токена — ошибка запуска, а не
открытый сервис. Неверный адрес (`runner:8090` без схемы) тоже валит старт
(`runner.ValidateRemoteURL`). Если сервис недоступен, `GET /api/editor/status`
возвращает `runner.available = false` с причиной, а интерфейс отключает кнопку
запуска и объясняет, почему.

Текст предупреждения тоже приходит с сервиса: в изолированном режиме это
«Код выполняется в изолированном контейнере без сети, с лимитами по времени,
памяти и размеру вывода» вместо честного «это не песочница» для локального
режима.

## 5. Безопасность

- у сервиса **нет** доступа к базе, ключам Supabase и JWT-секретам: в контейнер
  попадают только переменные `CODERUNNER_*`;
- сеть контейнера — внутренняя (`--internal`), без шлюза и DNS наружу: код
  ученика не может ни скачать пакеты, ни обратиться к чужим сервисам;
- запросы принимаются только с Bearer-токеном, сравнение — постоянного времени;
- тело запроса ограничено 2 МБ, неизвестные поля JSON отклоняются;
- ответ сервиса проверяется клиентом: статус, размер тела, отсутствие
  редиректов (редирект мог бы утащить токен на чужой хост);
- контейнер работает от непривилегированного пользователя с `--cap-drop=ALL`
  и `no-new-privileges`.

## 5a. Остаточный риск (честно)

Код ученика выполняется в том же контейнере, что и сервис, — отдельный контейнер
на каждый запуск не создаётся (для этого сервису понадобился бы доступ к
docker-сокету, а это уже привилегия уровня хоста). Что это значит:

- границы изоляции — контейнер, пользователь `10001`, лимиты CPU/RAM/pids/времени
  и отсутствие сети. Этого достаточно для учебного кода и защиты от случайных
  ошибок, но при компрометации ядра или побеге из контейнера код увидит процесс
  сервиса (в котором, однако, нет секретов API);
- для более сильной изоляции: `--runtime=runsc` (gVisor) или отдельный контейнер
  на задание через оркестратор (Kubernetes Job / Nomad), где сокет рантайма
  доступен платформе, а не сервису;
- интерфейс говорит ровно то, что есть: «отдельный контейнер без выхода в
  интернет, с лимитами», а не «полностью безопасная песочница».

## 6. Проверка

- `go test ./internal/runner/...` — протокол `RemoteRunner` (запуск, тесты,
  форматирование, статус, отказ без токена), валидация адреса, существующие
  тесты таймаута и лимита вывода. Эти тесты выполняет CI-job `backend`
  (`.github/workflows/ci.yml`: `gofmt`, `go vet`, `go build`, `go test` на
  `vendor/`) и он зелёный на коммите `ee494f8`+;
- **не проверено:** сам `backend/deploy/coderunner/Dockerfile` ни разу не
  собирался — в среде разработки нет Docker. Первая сборка образа — на стороне
  владельца, по шагам из раздела 3;
- вручную: `curl -H "Authorization: Bearer $TOKEN" -X POST
  http://127.0.0.1:8090/run -d '{"code":"package main\nimport \"fmt\"\nfunc main(){fmt.Println(1)}"}'`
  → `{"status":"ok","stdout":"1\n",...}`;
- бесконечный цикл `for {}` должен вернуть `status: "timeout"` в пределах ~11 с;
- `GET /api/editor/status` на проде должен содержать `"available": true` и
  предупреждение про контейнер.

## 7. Если контейнеры недоступны

На Vercel нет Docker-демона, поэтому сервис разворачивается отдельно
(Fly.io, Cloud Run, собственный хост) и подключается по `CODE_RUNNER_URL`.
Пока он не развёрнут, работает локальный режим — с ограничениями ресурсов, но
без песочницы; интерфейс явно об этом предупреждает, а не создаёт ложное
ощущение безопасности.
