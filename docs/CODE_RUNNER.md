# Запуск пользовательского Go-кода

Документ описывает, как Go Academy выполняет код пользователя: что уже
работает, какие лимиты действуют и что нужно сделать, чтобы вынести запуск в
изолированный сервис на контейнерах.

## 1. Что происходит сейчас

Код исполняется **внутри процесса Go-бэкенда** (`backend/internal/runner`):

```text
POST /api/editor/run        →  runner.Run(code)
POST /api/editor/format     →  gofmt (тот же раннер)
POST /api/exercises/{id}/submit → runner.Grade(code, тесты задания)
GET  /api/editor/status     →  доступность Go SDK + действующие лимиты
```

Алгоритм запуска:

1. Проверяется размер исходника (`MaxCode`, по умолчанию 256 КиБ) — до записи
   на диск.
2. Создаётся временный каталог внутри `WorkRoot` (по умолчанию `os.TempDir()`).
   Туда пишется `main.go`; при проверке задания — ещё `main_test.go` из
   `content/`.
3. Запуск ограничен по времени (`DefaultTimeout` — 10 с, для проверки задания
   плюс таймаут `go test`), вывод читается в `limitedBuffer` с потолком 256 КиБ
   на поток; при превышении процесс убивается, в ответе `truncated: true`.
4. Одновременно выполняется не больше `DefaultConcurrency = 2` программ; при
   заполненной очереди запрос ждёт слот не дольше `QueueTimeout` (15 с), затем
   отвечает `timeout`.
5. Каталог запуска удаляется, `go build` использует общий `GOCACHE`, чтобы
   каждый запуск не компилировал стандартную библиотеку заново.

## 2. Чего это не даёт

Это **ограничение ресурсов, а не песочница**. Код выполняется от того же
пользователя, что и сервер, и имеет доступ к файловой системе, переменным
окружения и сети процесса.

Поэтому:

- секреты (`SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_DB_URL`, JWT-секреты) **не
  должны** находиться в окружении процесса, выполняющего код. Сейчас сервер
  читает их при старте, поэтому при включении публичного запуска кода они
  должны быть перенесены в отдельный сервис;
- `/api/editor/status` честно возвращает `runner.warning` с этим
  предупреждением, а веб- и мобильный интерфейсы показывают его пользователю;
- `GoBinary` можно явно задать в конфигурации (`runner.Config.GoBinary`), пустое
  значение включает автопоиск; если Go не найден, `runner.available = false` и
  интерфейс отключает кнопку запуска вместо «мёртвой» кнопки.

## 3. Почему пока не контейнер

Vercel Functions (и локальный `go run`) не дают запускать Docker: в среде
исполнения нет демона контейнеров, а файловая система доступна только на
запись в `/tmp`. Контейнерный запуск — отдельный сервис, который разворачивается
не на Vercel.

## 4. Целевая архитектура сервиса

```text
Web / Mobile
   │  POST /api/editor/run (JWT Supabase)
   ▼
Go-API (Vercel)  ── proxy ──►  Code Runner (Fly.io / Cloud Run / собственный VM)
                                        │
                                        ▼
                              container (tmpfs, no network)
                              go build → run внутри container
```

Требования к сервису:

| Требование | Значение по умолчанию | Комментарий |
| --- | --- | --- |
| CPU | 0.5 vCPU | `--cpus=0.5` |
| RAM | 256 МБ | `--memory=256m --memory-swap=256m` |
| Время | 10 с на выполнение, 40 с на сборку | жёсткий kill по таймауту |
| Размер исходника | 256 КиБ | проверка до запуска |
| Размер вывода | 256 КиБ на поток | обрезка + `truncated` |
| Сеть | выключена | `--network=none` |
| Файловая система | read-only образ + tmpfs для `/tmp` | `--read-only --tmpfs /tmp` |
| Пользователь | непривилегированный (`nobody`) | `--user 65534:65534` |
| Переменные окружения | только `PATH`, `HOME` внутри контейнера | без секретов |
| Параллелизм | 2 на инстанс | ограничение семафором |

Дополнительно: `--cap-drop=ALL`, `--security-opt=no-new-privileges`,
`--pids-limit=64`, `GOMAXPROCS=1`, `GOFLAGS=-mod=mod`.

## 5. Как переключиться

Раннер уже отделён интерфейсом (`Run`, `Format`, `Grade`, `Status`), поэтому
переключение — замена реализации:

1. Добавить в `backend/internal/runner` клиент удалённого сервиса
   (`RemoteRunner`) с тем же набором методов и таймаутами.
2. Выбрать реализацию по переменной окружения `CODE_RUNNER_URL`: пусто —
   локальный раннер, задано — удалённый.
3. Прокси-эндпоинты (`/api/editor/*`, `/api/exercises/{id}/submit`) не меняются,
   клиенты web и mobile продолжают работать без изменений.
4. Секреты бэкенда перестают пересекаться с раннером: у сервиса свой набор
   переменных, только `CODE_RUNNER_TOKEN` для аутентификации прокси.

Лимиты и тексты предупреждений остаются в одном месте — `runner.Limits()` и
`runner.Status()`, поэтому интерфейс автоматически покажет новые значения.

## 6. Проверка

- `backend/internal/runner/runner_test.go` — таймаут убивает программу,
  лимит вывода обрезает поток, размер исходника проверяется до запуска;
- ручная проверка: `curl -H "Authorization: Bearer $TOKEN" -X POST
  https://<host>/api/editor/run -d '{"code":"package main\nfunc main(){for{}}"}'
  должен вернуть `status: "timeout"` в пределах ~11 секунд;
- `GET /api/editor/status` — источник правды для интерфейса о доступности и
  лимитах.
