# Архитектура Go Academy 2.0

## 1. Принципы

1. **Один backend, три клиента.** Supabase (Auth + Postgres + RLS) и Go-сервис
   остаются единственным источником правды. Web, iOS и Android читают одни и те
   же `/api/*` эндпоинты. Второй backend, второй auth или вторая схема прогресса
   не создаются.
2. **Контент отдельно от кода.** Уроки, задачи, колоды и викторины лежат в
   `content/` и читаются Go-сервисом (локально с диска, на Vercel — из
   встроенного бинарника). Обе платформы получают их через API, поэтому контент
   гарантированно одинаков.
3. **Совместимость важнее «правильной» структуры.** Существующие каталоги
   `backend/`, `frontend/`, `content/` остаются на месте: от них зависят
   `vercel.json`, Makefile, скрипты и Go-тест деплоя.
4. **Никаких моков вместо интеграций.** Если возможности нет (запуск Go на
   телефоне, sandbox для кода), интерфейс это показывает явно.

## 2. Схема

```text
┌───────────────┐        ┌───────────────┐        ┌───────────────┐
│  Web (React)  │        │ iOS (Expo)    │        │ Android (Expo)│
│  frontend/    │        │    mobile/    │        │    mobile/    │
└───────┬───────┘        └───────┬───────┘        └───────┬───────┘
        │  fetch /api (Bearer)   │  fetch /api (Bearer)   │
        └───────────────┬────────┴────────────────────────┘
                        ▼
              ┌───────────────────┐
              │  Go API + SPA     │  backend/  (Vercel Services)
              │  auth, progress,  │
              │  content, runner  │
              └─────────┬─────────┘
                        │ pgx (session pooler)
                        ▼
              ┌───────────────────┐
              │ Supabase Postgres │  RLS по auth.uid()
              │ + Supabase Auth   │
              └───────────────────┘
```

Клиенты обращаются к Supabase Auth напрямую (получение и refresh токена), а к
данным — через Go API, который проверяет токен и открывает транзакцию с ролью
`authenticated` и claims пользователя. Поэтому политики RLS работают одинаково
для всех клиентов, а бизнес-логика (идемпотентность, начисления, SM-2) не
дублируется на клиентах.

## 3. Общие пакеты

```text
packages/
├── shared-types/        DTO API, доменные типы, статусы уроков и карточек
├── shared-utils/        форматирование (время, числа, даты, склонения)
├── shared-learning/     прогресс, план на день, серия, SM-2 (зеркало сервера)
├── shared-validation/   проверки email/пароля, настроек, заметок, кода
└── shared-content/      структура контента: курсы, модули, уроки, навигация
```

Каждый пакет — исходники TypeScript без отдельного шага сборки:

- **web** подключает их через alias `@shared/*` в `vite.config.ts` и `paths` в
  `tsconfig.app.json`; Vite компилирует их как часть приложения.
- **mobile** подключает через `paths` в `tsconfig.json` + `watchFolders` и
  `extraNodeModules` в `metro.config.js`.

Такой вариант не меняет lock-файл и не ломает `npm ci` на Vercel, в отличие от
перехода на npm workspaces.

Что попадает в пакеты, а что нет:

| В пакеты | Остаётся на платформе |
| --- | --- |
| типы DTO и доменные модели | UI-компоненты, стили, темы |
| форматирование и склонения | навигация (React Router / Expo Router) |
| расчёт прогресса, серии, плана, SM-2 для превью | Monaco / мобильный редактор |
| валидация форм и настроек | работа с SecureStore / SQLite |
| структура контента и навигация по урокам | запросы к API, кэш, стор |

## 4. Backend

Слои (без изменений по сути, только аддитивные правки):

```text
cmd/server → config → database (миграции) → api (routes, middleware, handlers)
                                              ├── storage (SQL)
                                              ├── course/practice/cards/quizzes (контент)
                                              ├── progress (статистика, план, серия)
                                              └── runner (Go-код, go test)
```

Правила:

- новые поля БД — только `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` в
  `internal/database/migrate.go` + зеркально в `schema_pg.sql` и `schema_sqlite.sql`;
- новые эндпоинты — под `/api`, с проверкой владельца и RLS;
- публичные эндпоинты перечислены в `isPublicPath` (`/api/health`,
  `/api/config`, `/api/config.js`), всё остальное требует токен.

## 5. Mobile

```text
mobile/
├── app/                        файловая маршрутизация Expo Router
│   ├── (auth)/login|register|reset.tsx
│   ├── (tabs)/index|learn|code|cards|profile.tsx
│   ├── lesson/[lessonId].tsx, exercise/[exerciseId].tsx
│   └── notes.tsx, quizzes.tsx, achievements.tsx, settings.tsx
├── src/
│   ├── api/                    клиент Go-API с Bearer и refresh
│   ├── auth/                   Supabase-сессия, SecureStore
│   ├── db/                     expo-sqlite: кэш контента, журнал изменений, очередь
│   ├── sync/                   отправка очереди, разрешение конфликтов
│   ├── ui/                     нативные компоненты и дизайн-токены
│   ├── store/                  Zustand: настройки и тема
│   ├── hooks/                  useCachedQuery: кэш сначала, сеть потом
│   ├── lib/                    конфигурация, склейка Markdown
│   └── features/notifications/ Expo Notifications: opt-in напоминания
└── app.config.ts, eas.json, metro.config.js
```

Почему не WebView: основной сценарий мобильного — чтение урока и повторение
карточек одной рукой. WebView с Monaco тянет 3.3 МБ JS, не даёт нативной
клавиатуры и ломает жесты. Редактор на телефоне — отдельный экран с
подсветкой и панелью символов; запуск кода идёт через тот же `/api/editor/run`.

## 6. Офлайн и синхронизация

- **Чтение.** Контент (курс, уроки, колоды, викторины) и последние ответы API
  кэшируются в SQLite; при отсутствии сети экраны читают кэш и показывают
  плашку «офлайн».
- **Запись.** Действия, которые можно отложить (отметка урока, прогресс чтения,
  заметки, оценки карточек, время обучения), пишутся сначала в локальный журнал
  `pending_ops` с `op_id` (UUID) и временем, затем отправляются на сервер.
- **Идемпотентность.** Повторная отправка `op_id` не создаёт дубль: серверные
  операции уроков и повторений карточек уже идемпотентны по смыслу (статус
  урока — по последнему значению, повторение карточки — одна запись на
  `op_id`), заметки — по `updated_at` (последняя запись побеждает).
- **Конфликты.** Для «последняя запись побеждает» используется
  max(`updated_at`); для карточек расписание пересчитывает сервер, клиент
  отправляет только оценку — это исключает двойное планирование при
  синхронизации с двух устройств.
- **Повторы.** Экспоненциальная пауза (2 с → 5 мин), ограничение попыток,
  ручной retry в профиле.
- **Время.** «Сегодня» и дни активности считаются в часовом поясе приложения
  (`APP_TIMEZONE`, по умолчанию `Europe/Moscow`): на Vercel процессы живут в
  UTC, и без явного пояса серия рвалась бы вечером по местному времени. Серия
  сравнивает календарные дни, поэтому переходы на летнее/зимнее время её не
  обрывают.

Подробности — `docs/SYNC.md`.

## 7. Безопасность

- publishable/anon ключ Supabase — публичный, приходит из сборки или `/api/config`;
- `service_role` ключ не используется ни в web, ни в mobile;
- все пользовательские данные защищены RLS; критичные операции (начисления,
  SM-2, проверка задания) выполняются на сервере;
- запуск пользовательского Go-кода — отдельный сервис (см. `docs/CODE_RUNNER.md`),
  сейчас это подпроцесс с таймаутами и лимитами, но без контейнерной изоляции;
  API помечает это ограничение в `/api/editor/status`.

## 8. Деплой

- **Web**: Vercel Services, `vercel.json` в корне (backend + frontend),
  переменные проекта (`SUPABASE_*`, `PUBLIC_KEY`), конфигурация фронтенда может
  приходить из `/api/config.js`.
- **Mobile**: EAS Build (профили `development`, `preview`, `production`),
  bundle identifier `com.goacademy.app`, package `com.goacademy.app`, конфигурация
  Supabase через `app.config.ts` (`extra` → `expo-constants`), OTA-обновления
  через EAS Update — опционально.
