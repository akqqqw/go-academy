# Деплой на Vercel

Пошаговый чек-лист: от чистого репозитория до работающего приложения на
`https://<project>.vercel.app`. Техническое описание того, как устроена
конфигурация, — в разделе [«Деплой на Vercel»](../README.md#деплой-на-vercel)
README.

## Что разворачивается

Один проект Vercel, два сервиса (Vercel Services, beta). Состав и маршрутизация
описаны в `vercel.json` в корне репозитория, менять их в панели не нужно.

| Сервис | Что это | Куда приходят запросы |
| --- | --- | --- |
| `frontend` | статика Vite (`frontend/dist`) | всё, кроме `/api/*`; неизвестные пути отдают `index.html` |
| `backend` | Go-сервер (`backend/cmd/server`) | `/api/*` с тем же путём |

Браузер обращается только к относительному `/api`, поэтому домены, CORS и адреса
бэкенда настраивать не нужно.

## 0. Что понадобится

- аккаунт Vercel (тариф Hobby подходит);
- проект Supabase (бесплатного тарифа достаточно);
- репозиторий на GitHub с этим кодом;
- Node.js 20+ локально — только если деплоите через CLI.

## 1. Подготовьте Supabase

1. **Authentication → Sign In / Providers → Email**: включите провайдер.
   Приложение рассчитано на вход сразу после регистрации, поэтому **Confirm
   email** лучше выключить (если он включён, письмо с подтверждением должно
   доходить, а ссылка вести на домен Vercel — см. пункт 2).
2. **Project Settings → API**: скопируйте **Project URL** и **publishable key**
   (подойдёт и legacy `anon` key).
3. **Project Settings → Database → Connect**: выберите **Session pooler** и
   скопируйте строку подключения. Прямое подключение к `db.<ref>.supabase.co`
   (IPv6-only) из serverless-окружения Vercel обычно не работает — нужен именно
   pooler с IPv4.
4. Пароль БД, если он неизвестен, сбрасывается там же (**Reset database
   password**) — после сброса обновите строку подключения в Vercel.

Схема таблиц, RLS-политики и гранты создаются автоматически при первом запуске
backend, отдельно применять SQL не нужно.

## 2. Настройте домены в Supabase Auth

В **Authentication → URL Configuration**:

- **Site URL**: `https://<project>.vercel.app`;
- **Redirect URLs**:
  - `https://<project>.vercel.app/**` — продакшн;
  - `https://*-<team-slug>.vercel.app/**` — превью-деплои (подставьте свой
    team slug из адреса превью-ссылки);
  - `http://localhost:5173/**` — локальная разработка.

Без этого ссылки из писем (подтверждение адреса, сброс пароля) будут вести на
`localhost` или открывать ошибку «redirect not allowed».

## 3. Импортируйте проект в Vercel

1. **Add New → Project** → выберите репозиторий.
2. **Root Directory** оставьте корнем репозитория: `vercel.json` читается только
   из корня, а каталоги сервисов (`backend`, `frontend`) заданы в нём.
3. **Framework Preset**: `Other` (или любое автоопределение) — пресеты и команды
   сборки для каждого сервиса уже прописаны в `vercel.json`, ручные настройки
   Build & Output Settings игнорируются.
4. **Environment Variables** — задайте на уровне проекта, они общие для обоих
   сервисов:

| Переменная | Значение | Кому нужна |
| --- | --- | --- |
| `SUPABASE_DB_URL` | строка подключения Session pooler | backend (runtime) |
| `PUBLIC_KEY` | publishable/anon key | backend (проверка токенов) |
| `VITE_SUPABASE_URL` | `https://<ref>.supabase.co` | frontend (встраивается при сборке) |
| `VITE_SUPABASE_ANON_KEY` | publishable/anon key | frontend (встраивается при сборке) |

Необязательные: `SUPABASE_URL` (выводится из `postgres.<ref>` в строке
подключения), `SUPABASE_ANON_KEY` (алиас `PUBLIC_KEY`), `CONNECTION_URL` (алиас
`SUPABASE_DB_URL`), `GOACADEMY_REQUIRE_AUTH` (по умолчанию `1`; `0` отключает
вход — только для отладки), `GOACADEMY_CORS_ORIGINS` (в продакшене не нужен).

Отмечайте переменные для **Production**, **Preview** и **Development**: превью
и продакшн-деплои используют одни и те же значения, то есть одну и ту же базу.

`VITE_*` попадают в статику на этапе `npm run build`. Если изменить их после
деплоя, Vercel пересоберёт фронтенд при следующем деплое — само по себе
изменение переменной уже запускает новую сборку.

5. Нажмите **Deploy**.

## 4. Деплой через CLI (альтернатива панели)

```bash
npx vercel login
npx vercel link                # привязать каталог к проекту

# переменные окружения (по одной на команду)
npx vercel env add SUPABASE_DB_URL production
npx vercel env add PUBLIC_KEY production
npx vercel env add VITE_SUPABASE_URL production
npx vercel env add VITE_SUPABASE_ANON_KEY production

npx vercel                     # превью-деплой
npx vercel --prod              # продакшн
```

CLI загружает каталог целиком, поэтому локальные артефакты (`node_modules`,
`dist`, `data/`, `*.db`) исключены через `.vercelignore`. Каталог `.vercel/`
создаётся командой `link` и в git не попадает.

## 5. Проверка после первого деплоя

```bash
curl -sS https://<project>.vercel.app/api/health
# {"status":"ok","version":"0.1.0","time":"..."}
```

`/api/health` пингует базу: `status: "ok"` — схема применена, соединение с
Supabase работает; `degraded` и код 503 — база недоступна (см. диагностику).
Первый запрос после деплоя самый долгий: Go-сервис стартует, распаковывает
встроенный контент в `/tmp` и применяет миграции в Supabase. На пустой базе это
может занять десятки секунд — прогрейте эндпоинт перед тем, как открывать сайт.

Дальше по шагам:

1. откройте `https://<project>.vercel.app` — должен загрузиться экран входа;
2. зарегистрируйте пользователя и войдите;
3. проверьте главную (данные приходят из Supabase), урок, заметку, карточку,
   викторину и достижения;
4. перезагрузите страницу с глубокой ссылкой (`/learning/m03-01`) — SPA должна
   открыться, а не 404;
5. обновите страницу — сессия должна сохраниться.

## Что на Vercel работает, а что нет

| Раздел | Статус | Причина |
| --- | --- | --- |
| Уроки, программа, главная, прогресс, заметки, карточки, викторины, достижения, настройки | работает | данные в Supabase |
| Вход и регистрация | работает | Supabase Auth |
| Чтение и сохранение кода в редакторе | работает | `/api/drafts` в Supabase |
| **Запуск кода** и **проверка решений через `go test`** | **не работает** | в образе сервиса нет Go-тулчейна; редактор вернёт понятное сообщение «Go не найден» |
| `/api/backup` | отвечает `501` | резервные копии делает сам Supabase |

Запуск Go-кода требует установленного `go` в контейнере сервиса. Если он нужен в
облаке, единственный путь — собирать backend как контейнер (`runtime:
"container"` в `vercel.json`) с образом, где есть Go, либо держать отдельный
сервер вне Vercel. Контент уроков, практика и остальные разделы от этого не
зависят.

## Особенности serverless, о которых нужно помнить

- **Файловая система только для чтения, кроме `/tmp`.** База и пользовательские
  данные лежат в Supabase; в `/tmp` распаковывается только контент уроков. Записи
  в `/tmp` не переживают холодный старт, и это нормально.
- **Изменения в `content/` требуют пересборки backend.** Контент встраивается в
  бинарник командой сборки (`go:embed`), поэтому обновление уроков, карточек,
  викторин и заданий в репозитории доедет до продакшна только с новым деплоем.
- **Лимит тела запроса** — 4,5 МБ на запрос. Черновики кода ограничены 256 КБ,
  так что лимит не мешает.
- **Превью-деплои используют ту же базу**, что и продакшн. Если нужна
  изоляция — заведите отдельный Supabase-проект и переменные для окружения
  Preview.
- **Холодный старт.** После простоя первый запрос дольше обычного: старт
  Go-сервиса, распаковка контента и проверка схемы.

## Обновление и откат

- Обычный `git push` в `main` → продакшн-деплой; пуш в другую ветку → превью.
- Откат: **Deployments** → нужный деплой → **⋯ → Promote to Production**
  (или **Rollback**). База при откате кода не откатывается: схема
  миграции идемпотентна и совместима назад.

## Диагностика

| Симптом | Причина и что делать |
| --- | --- |
| `/api/health` → `degraded`, 503 | backend не видит базу: проверьте `SUPABASE_DB_URL` (Session pooler, пароль после reset), лимиты Supabase |
| Все `/api/*` → 503 `auth_not_configured` | не задан `PUBLIC_KEY` (или `SUPABASE_ANON_KEY`) для сервиса backend |
| Все `/api/*` → 401 `unauthorized` | нет сессии в браузере или `VITE_*` не попали в сборку — фронтенд не смог войти |
| Белый экран, в консоли `Supabase не настроен` | не заданы `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` на момент сборки; задайте и пересоберите (Redeploy) |
| 404 на `/learning/...`, `/practice`, `/settings` | сломаны `rewrites` в `vercel.json`; конфигурация проверяется тестом `backend/internal/deploy/vercel_test.go` |
| `/api/*` отдаёт HTML фронтенда | правило `/api/(.*)` в корне `vercel.json` переставлено ниже catch-all; API-правило должно быть первым |
| Сборка backend падает на `cp: cannot stat '../content'` | у сервиса неверный **Root Directory**; корень репозитория обязателен |
| Сборка backend падает на `go:embed` / `pattern assets: no matching files` | в `buildCommand` потерялся шаг копирования `content/` в `internal/contentfs/assets` |
| Редактор: «Go не найден» | ожидаемо на Vercel (см. таблицу выше) |
| Ссылка из письма ведёт на `localhost` | не настроены Site URL / Redirect URLs в Supabase Auth (пункт 2) |

## Локальная проверка той же сборки

```bash
cd backend
rm -rf internal/contentfs/assets && mkdir -p internal/contentfs/assets
cp -R ../content/. internal/contentfs/assets/
go build -tags vercel -o server ./cmd/server
VERCEL=1 PORT=3999 ./server    # 0.0.0.0:3999, база из SUPABASE_DB_URL
```

Для обычной разработки удобнее `make dev` (backend + Vite с проксированием
`/api`), а `vercel dev` не обязателен.
