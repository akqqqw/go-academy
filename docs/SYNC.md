# Офлайн-режим и синхронизация

Мобильное приложение работает без сети: читает кэш, записывает действия в
локальный журнал и отправляет их, когда соединение возвращается. Сервер
(Supabase + Go-API) остаётся единственным источником правды — локальные данные
никогда не перетирают более свежие серверные.

## 1. Слои

```text
экран ──► src/hooks/use-cached-query ──► SQLite cache_entries ──► GET /api/*
   │                                              ▲
   └──► действие ──► src/sync/queue.pending_ops ──┘ (flush при сети/фореграунде)
                              │
                              └──► POST /api/* (идемпотентно)
```

| Модуль | Ответственность |
| --- | --- |
| `src/db/database.ts` | открытие SQLite, миграции `user_version`, `resetLocalData()` |
| `src/db/cache.ts` | `cacheSet` / `cacheGet(ttl)` / `cacheUpdatedAt`, локальные статусы уроков и позиция чтения |
| `src/sync/queue-core.ts` | чистая логика: задержки повторов, схлопывание операций, разрешение конфликтов |
| `src/sync/queue.ts` | `enqueue`, `pendingOps`, `flushQueue`, `clearFailedOps` |
| `src/sync/sync-context.tsx` | состояние сети (expo-network), опрос каждые 30 с, возврат в фореграунд |
| `src/hooks/use-cached-query.ts` | «кэш сначала, сеть потом» + `refresh()` |

## 2. Формат очереди

```ts
type PendingKind =
  | 'lesson_opened'      // урок открыт
  | 'lesson_completed'   // урок завершён
  | 'lesson_scroll'      // позиция чтения (никогда не уходит на сервер)
  | 'study_ping'         // секунды учёбы
  | 'note_save'          // правка заметки
  | 'card_review'        // оценка карточки

interface PendingOp {
  op_id: string        // UUID, ключ идемпотентности
  kind: PendingKind
  payload: unknown
  created_at: number
  attempts: number
  next_try_at: number
  last_error?: string | null
}
```

`op_id` генерируется на клиенте (`expo-crypto.randomUUID()`), поэтому повторная
отправка после сбоя не создаёт дубль.

## 3. Схлопывание (compaction)

Перед отправкой очередь «сжимается» (`compact`), чтобы не гонять по сети
лишние операции:

| Ситуация | Результат |
| --- | --- |
| урок открыт → прокручен → завершён | остаётся только `lesson_completed` (приоритет 3 > 2 > 1) |
| открытие пришло после завершения | завершение сохраняется, статус не понижается |
| несколько `lesson_scroll` одного урока | остаётся последняя позиция |
| несколько `study_ping` | суммируются, но не больше 900 с (лимит одного пинга) |
| несколько `note_save` одной заметки | остаётся последняя версия |
| `card_review` | **не схлопываются**: две оценки одной карточки — два события обучения |

## 4. Идемпотентность на сервере

| Операция | Почему повтор безопасен |
| --- | --- |
| `lesson_opened` / `lesson_completed` | статус записывается как значение, а не инкремент; `completed_at` ставится один раз |
| `study_ping` | секунды добавляются к `activity_days(day)` через `ON CONFLICT ... DO UPDATE`, ограничение 900 с на пинг защищает от накрутки |
| `note_save` | последняя запись побеждает по `updated_at`; сравнение делает клиент (`localWins`) |
| `card_review` | сервер считает SM-2 один раз на полученную оценку; повторная отправка с тем же `op_id` не создаёт второй `card_reviews` |

Расписание карточек **никогда** не считается на клиенте: два устройства
посчитали бы интервалы по-разному. Клиент отправляет только оценку
(`again` / `hard` / `good` / `easy`), сервер возвращает `ReviewResult` с новым
`due_at`.

## 5. Повторы и ошибки

Задержки: **2 с → 10 с → 1 мин → 5 мин → 15 мин**, максимум `MAX_ATTEMPTS = 6`
попыток (`src/sync/queue-core.ts`).

- `flushQueue` останавливается на первой сетевой ошибке — нет смысла долбить
  сервер, когда пропал интернет;
- при логической ошибке (4xx) операция увеличивает `attempts` и уходит в
  отложенные; после 6 попыток считается «застрявшей» и не блокирует очередь;
- «застрявшие» операции видны в профиле и снимаются кнопкой
  «Очистить неудачные» (`clearFailedOps`).

## 6. Конфликты

| Данные | Правило |
| --- | --- |
| Заметки | last-write-wins по `updated_at` (`localWins(local, remote)`); при равных метках побеждает локальная версия |
| Статус урока | монотонно: `completed` не понижается до `in_progress` |
| Настройки | оптимистичное обновление с откатом: при ошибке возвращается предыдущее значение и показывается сообщение |
| Карточки | сервер — единственный планировщик, конфликта интервалов нет |

## 7. Что кэшируется и на сколько

| Ключ | TTL | Почему |
| --- | --- | --- |
| `dashboard` | 0 (всегда свежий, но кэш используется при офлайне) | главные цифры должны быть актуальны |
| `course` | 0 | состав курса меняется только с деплоем |
| `lesson-content:<id>` | 0 | текст урока неизменен между деплоями |
| `flashcards`, `quizzes`, `notes`, `achievements`, `progress` | 0 | показываем кэш сразу, затем обновляем |
| `settings` | бессрочно | без настроек приложение не должно «мигать» темой |

TTL `0` означает «сначала отдать кэш, затем обязательно обновить из сети» —
именно это делает `useCachedQuery`.

## 8. Очистка

- при выходе из аккаунта (`signOut`) вызывается `resetLocalData()`: удаляются
  `cache_entries`, `pending_ops`, `lesson_progress`, `settings_cache`;
- вручную — «Сбросить локальный кэш» в настройках (с подтверждением);
- прогресс в Supabase при этом не затрагивается.

## 9. Как проверить

1. `cd mobile && npm test` — 17 тестов `queue-core.test.ts` (задержки, схлопывание,
   `localWins`) + тесты разбора Markdown и текстов напоминаний.
2. Ручной сценарий: включить авиарежим → открыть урок, отметить пройденным,
   поставить оценку карточке → в профиле «N изменений ждут синхронизации» →
   выключить авиарежим → через ≤30 с очередь пуста, цифры на главной совпадают
   с сервером.
