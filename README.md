# 🚀 Go Academy

Личная платформа для самостоятельного изучения **Go**: программа из 14 модулей,
статистика, дневные цели и календарь активности. Вход по email и паролю через
**Supabase Auth**, а весь прогресс, заметки и карточки хранятся в **Supabase
Postgres** и доступны с любого устройства.

> **Текущий статус: этапы 1–9 завершены — основа приложения, все 104 урока в
> 14 модулях, встроенный редактор с настоящим запуском Go-кода, 30 практических
> задач с проверкой через `go test`, заметки в Markdown, 100 карточек в
> 12 колодах с повторением SM-2, 6 викторин с разбором ответов и 23 достижения.**
> Остался этап 10 (экспорт/импорт и полировка); разделы, которые ещё не готовы,
> честно сообщают об этом и не содержат фиктивных кнопок. Подробнее — в разделе
> [Дорожная карта](#дорожная-карта).

## Технологии

**Frontend:** React 19, TypeScript, Vite 7, Tailwind CSS 4, компоненты в стиле
shadcn/ui (Radix UI), Zustand, TanStack Query, React Router 7, Lucide Icons, Sonner.
Тесты — Vitest + Testing Library.

**Backend:** Go (стандартная библиотека `net/http`, `log/slog`), Supabase Postgres
через [`github.com/jackc/pgx/v5`](https://github.com/jackc/pgx), проверка
access-токенов Supabase Auth. SQLite
([`github.com/ncruces/go-sqlite3`](https://github.com/ncruces/go-sqlite3)) остаётся
только для тестов хранилища — SQLite скомпилирован в WebAssembly, поэтому cgo не нужен.

## Быстрый старт

Требования:

- **Go 1.23+** (проверено на Go 1.27),
- **Node.js 20+ и npm**,
- проект **Supabase** (бесплатного тарифа достаточно),
- браузер (Chrome, Firefox, Safari, Edge).

### 1. Настройте Supabase

1. Создайте проект на [supabase.com](https://supabase.com/dashboard).
2. **Authentication → Sign In / Providers → Email**: включите провайдер и
   выключите **Confirm email** — приложение рассчитано на вход сразу после
   регистрации.
3. **Project Settings → API**: скопируйте Project URL и **publishable key**
   (подойдёт и legacy `anon` key).
4. **Project Settings → Database → Connect**: выберите **Session pooler** и
   скопируйте строку подключения. Пароль БД можно сбросить там же
   (**Reset database password**), если он неизвестен.

Создайте два локальных файла (оба в `.gitignore`):

```bash
# .env в корне проекта — для backend
cat > .env <<'EOF'
PUBLIC_KEY=sb_publishable_ваш_ключ
CONNECTION_URL=postgresql://postgres.<ref>:<пароль>@aws-0-<region>.pooler.supabase.com:5432/postgres
EOF

# frontend/.env.local — для Vite
cat > frontend/.env.local <<'EOF'
VITE_SUPABASE_URL=https://<ref>.supabase.co
VITE_SUPABASE_ANON_KEY=sb_publishable_ваш_ключ
EOF
```

Backend сам выводит `SUPABASE_URL` из имени пользователя `postgres.<ref>` в
строке подключения. Схема таблиц, RLS-политики и гранты создаются при первом
запуске. Шаблоны этих файлов лежат в `.env.example` и `frontend/.env.example`.

### 2. Запустите приложение

```bash
git clone https://github.com/akqqqw/go-academy.git
cd go-academy

# один раз — зависимости фронтенда
npm --prefix frontend install

# запуск backend + Vite в dev-режиме
make dev
```

- Интерфейс: **http://localhost:5173** (Vite проксирует `/api` на backend).
- API: **http://127.0.0.1:8080/api**.

Без Make:

```bash
# терминал 1
cd backend && go run ./cmd/server --data ../data --content ../content

# терминал 2
cd frontend && npm run dev
```

Без входа доступны только `/login` и `/register`; все остальные маршруты и
`/api/*` (кроме `/api/health`) требуют действующую сессию Supabase.

## Продакшн-запуск на одном порту

```bash
make build      # фронтенд → frontend/dist, backend → backend/bin/go-academy
make run        # соберёт и запустит на http://127.0.0.1:8080
```

Либо вручную:

```bash
cd frontend && npm run build
cd ../backend && go build -o bin/go-academy ./cmd/server
./bin/go-academy --data ../data --content ../content --frontend ../frontend/dist
```

Backend отдаёт собранный SPA, поддерживает клиентскую маршрутизацию (fallback на
`index.html`) и JSON-ошибки для неизвестных `/api`-маршрутов (404/405).

Учебный контент отделён от кода: программа курса лежит в `content/course.json`,

открытии — правки видны сразу.

### Формат файла урока

Front matter — это JSON между двумя строками `---`, затем обычный Markdown с
поддержкой таблиц (GFM) и блоков кода ` ```go `:

```markdown
---
{
  "title": "Что такое Go",
  "summary": "Короткое описание для карточки урока.",
  "minutes": 10,
  "objectives": ["Первая цель", "Вторая цель"]
}
---
## Теория

Текст урока с примерами:

```go
package main

import "fmt"

func main() {
	fmt.Println("Привет")
}
```

## Практика

Задание, стартовый код, ожидаемый вывод и подсказка.

## Резюме

- Ключевой вывод урока.
```

Обязательны `title`, хотя бы одна цель и непустой текст; остальные поля
подставляются из `course.json`. Проверки в Go-тестах требуют, чтобы каждый
готовый урок содержал разделы «Практика» и «Резюме» и блок кода. Некорректный
файл не ломает сервер: API вернёт `content_invalid` с понятным сообщением.

## Практика и проверка решений

### Формат задания

```
{
  "id": "sum-two",
  "module": "m02",
  "title": "Сумма двух чисел",
  "summary": "Арифметика, параметры и возвращаемое значение.",
  "difficulty": "easy",
  "topics": ["операторы", "функции"],
  "minutes": 5,
  "statement": "## Условие\n…Markdown…",
  "starter_code": "package main\n\nfunc Sum(a, b int) int { … }",
  "hints": ["Сложение двух int работает напрямую."],
  "solution": "package main\n…эталон…",
  "tests": "package main\n\nimport \"testing\"\n\n// TestSumPositive складывает…\nfunc TestSumPositive(t *testing.T) { … }"
}
```

Заголовок проверки берётся из комментария перед функцией `Test*` — именно он
показывается ученику вместо имени теста. Файл проверяется при загрузке: известен
ли модуль, уникален ли `id`, есть ли тесты, подсказки и эталонное решение.

Задания лежат отдельно от кода — в `content/exercises/exercises.json`. Каждое
задание содержит условие в Markdown, стартовый код, подсказки, эталонное
решение и файл Go-тестов. **Тесты и решение в браузер не отправляются**: иначе
проверку можно было бы обойти, подогнав ответ под конкретные assert-ы.

| Что | Где |
| --- | --- |
| Каталог заданий и проверка контента | `backend/internal/practice` |
| Запуск проверок | `backend/internal/runner/grade.go` (`go test -json`) |
| История попыток в Supabase | `backend/internal/storage/exercises.go`, таблица `exercise_attempts` |
| Список с фильтрами и статистикой | `frontend/src/pages/practice-page.tsx` |
| Страница решения | `frontend/src/pages/exercise-page.tsx` |
| Панель результатов | `frontend/src/components/editor/test-results.tsx` |

Как устроена проверка:

1. решение и файл тестов пишутся в отдельный временный каталог (`main.go`,
   `exercise_test.go`);
2. запускается `go test -json -count=1 -timeout <лимит> main.go exercise_test.go`;
3. поток разбирается как JSON: `pass`/`fail` приходят по каждому тесту, а всё,
   что программа печатает сама, попадает в поле `Output` — подделать «PASS»
   текстом нельзя;
4. результат сопоставляется со списком ожидаемых тестов: если тест не
   отчитался (например, программа вызвала `os.Exit`), проверка не засчитывается;
5. ошибки сборки приходят событиями `build-output`/`build-fail` и превращаются в
   диагностики с номерами строк основного файла.

Дополнительно проверяются ресурсные лимиты (таймаут, размер вывода, очередь
запусков) и запрет `os/exec` — как и для свободного редактора. Первое успешное
решение увеличивает дневной счётчик решённых задач и попадает в план на сегодня;
повторные прохождения счётчик не трогают.

Содержание курса проверяется тестами: `TestRepositoryExercisesAreSolvable`
компилирует стартовый код каждого задания и прогоняет его тесты на эталонном
решении — так контент не может «сломаться» незаметно.

## Заметки

Раздел «Заметки» — личные записи в Markdown. Всё хранится в Supabase и доступно
с любого устройства после входа в аккаунт.

| Возможность | Как работает |
| --- | --- |
| Markdown | Редактор текста и предпросмотр с подсветкой блоков ` ```go `; заголовок берётся из первой непустой строки, если не задан явно |
| Папки | Две стартовые папки («Общее», «Уроки»), создание, переименование и удаление; при удалении папки заметки переезжают в «Общее», удалить «Общее» нельзя |
| Теги | До 12 тегов на заметку, нормализация (нижний регистр, `#` отбрасывается, дубликаты и недопустимые символы убираются), счётчики по тегам |
| Закрепление | Закреплённые заметки поднимаются в списке, есть фильтр «только закреплённые» |
| Поиск | Мгновенный поиск по заголовку и тексту, фильтры по папке, тегу и уроку работают одновременно |
| Автосохранение | Изменения уходят на сервер через 0,9 с после последней правки; кнопка «Сохранить» и `Ctrl+S` отправляют сразу, состояние («есть изменения», «сохраняем…», «сохранено», ошибка) видно в шапке редактора |
| Связь с уроками | На странице урока панель «Заметки к уроку»: кнопка «Добавить заметку» и «В заметку» для выделенного фрагмента теории — фрагмент сохраняется цитатой вместе с `lesson_id` |
| Статистика | Всего заметок, слов, папок, связанных с уроками; счётчики по папкам и тегам |

Поиск по кириллице работает через отдельную колонку `search_text`: нормализация
заголовка и текста делается в Go при сохранении, поэтому поиск одинаково работает
в Postgres и в SQLite-тестах. Лимиты: тело заметки — 200 КиБ, заголовок —
160 символов, тег — 32 символа; список отдаёт до 100 заметок по умолчанию и до
500 по запросу.

## Карточки и интервальное повторение

Колоды лежат в `content/flashcards/decks.json`, прогресс — в Supabase (`flashcards`,
`card_reviews`). При первом входе и при перечитывании контента карточки синхронизируются:
тексты обновляются, добавленные появляются, исчезнувшие удаляются, а выученный
прогресс сохраняется.

| Колода | Тема | Карточек |
| --- | --- | --- |
| `basics` | Основы синтаксиса | 9 |
| `types` | Типы и значения | 8 |
| `control` | Условия и циклы | 8 |
| `functions` | Функции и замыкания | 8 |
| `slices` | Массивы и слайсы | 9 |
| `maps` | Мапы и строки | 8 |
| `structs` | Структуры и методы | 9 |
| `interfaces` | Интерфейсы | 8 |
| `errors` | Ошибки и паника | 8 |
| `generics` | Дженерики | 8 |
| `concurrency` | Горутины и каналы | 10 |
| `toolchain` | Инструменты Go | 7 |

**Алгоритм (SM-2 с четырьмя оценками).** Для каждой карточки хранятся сложность
`ease` (по умолчанию 2.5, границы 1.3–3.0), интервал в днях, число повторений и
срывов:

| Оценка | Интервал | Сложность |
| --- | --- | --- |
| «Снова» | 0: карточка вернётся через 10 минут и в конец текущей сессии | −0.20 |
| «Трудно» | 1 день для новой, далее ×1.2 | −0.15 |
| «Хорошо» | 1 → 3 → интервал × сложность | без изменений |
| «Легко» | 4 дня для новой, далее × сложность × 1.3 | +0.15 |

Что есть в интерфейсе:

- сессия повторения с прогрессом, подсказкой, показом ответа по пробелу и
  оценками по клавишам `1`–`4`;
- счётчики «к повторению», «новых», «выучено» и прогресс по каждой колоде;
- точность, серия дней и график повторений за две недели;
- свои карточки в любой колоде (создание и удаление; карточки из контента
  защищены от удаления, их правят в JSON);
- сброс прогресса колоды с подтверждением;
- «Снова» возвращает карточку в конец текущей сессии, а на сервере планирует её
  через 10 минут.

## Викторины и тесты

Вопросы лежат в `content/quizzes/quizzes.json`, попытки — в Supabase (`quiz_attempts`).
Правильные ответы и объяснения **остаются на сервере**: `GET /api/quizzes/{id}`
отдаёт только текст вопроса и варианты, проверка происходит в `submit` и там же
возвращает разбор.

| Викторина | Модуль | Вопросов | Типы |
| --- | --- | --- | --- |
| `m01-basics` | 1 | 6 | single, multiple, true/false, input, code |
| `m02-functions` | 2 | 6 | single, multiple, true/false, input, code |
| `m03-collections` | 3 | 6 | single, multiple, true/false, input, code |
| `m05-interfaces` | 5 | 6 | single, multiple, true/false, input, code |
| `m08-concurrency` | 8 | 7 | single, multiple, true/false, input, code |
| `final-core` | итоговый | 7 | single, multiple, true/false, input, code |

**Пять типов вопросов**

| Тип | Что видит пользователь | Как считается |
| --- | --- | --- |
| `single` | варианты с одним выбором | верный вариант из `correct` |
| `multiple` | варианты с флажками | только полный набор: без пропусков и лишних |
| `true_false` | «Верно» / «Неверно» | значение `true` или `false` |
| `input` | поле ввода | нормализация: регистр, пробелы, кавычки, завершающая точка; список `accepted` |
| `code` | фрагмент Go с подсветкой и варианты ответа | как `single` |

Порог сдачи — 70%. После отправки показывается результат, разбор каждого вопроса:
что ответил пользователь, что было верно и почему (объяснение из контента).
Попытки сохраняются с длительностью и ответами; на странице списка видны лучший
результат, число попыток, средний балл и последние прохождения. Неполный набор
ответов отправлять можно — неотвеченные вопросы считаются ошибками.

## Данные, аккаунты и резервные копии

- **Аккаунты.** Регистрация и вход — email + пароль через Supabase Auth. Фронтенд
  хранит сессию и обновляет access-токен, backend проверяет токен запросом
  `GET /auth/v1/user` и кэширует результат на минуту. Пароль и email в базе
  приложения не хранятся.
- **Изоляция данных.** Каждая пользовательская таблица содержит `user_id uuid
  DEFAULT auth.uid()`; RLS-политики разрешают строки только владельцу. Backend
  открывает транзакцию запроса с `SET LOCAL ROLE authenticated` и claims
  пользователя в `request.jwt.claims`, поэтому даже ошибка в SQL не покажет чужие
  данные.
- **Персистентность.** Данные лежат в Supabase Postgres, а не в файловой системе
  сервера: прогресс сохраняется между перезапусками и доступен с разных устройств.
- **Первый вход.** Backend создаёт профиль и стартовые папки заметок, затем
  синхронизирует карточки из контента. Повторные запросы только читают профиль.
- **Миграции.** Схема Supabase создаётся при первом запуске идемпотентными
  statement'ами. Если соединение с pooler оборвётся, следующий запуск безопасно
  продолжит миграцию: уже созданные таблицы и политики не дублируются.
- **Резервные копии.** Их делает Supabase автоматически по расписанию тарифа
  (Project Settings → Database → Backups). Локальный `VACUUM INTO` для Postgres
  недоступен, поэтому `/api/backup` в облачном режиме отвечает `501`, а настройки
  показывают расположение бэкапов Supabase.
- **Локальная SQLite.** Осталась только для `go test` и режима разработки без
  аккаунтов (`GOACADEMY_REQUIRE_AUTH=0`). Рабочие данные пользователей туда не
  попадают.
- Время обучения учитывается только при активной вкладке (heartbeat раз в
  минуту, скрытая вкладка не считается).

**Сеть.** Приложению нужен доступ к Supabase (Auth и Postgres). Учебный контент,
шрифты, иконки и Monaco загружаются локально — внешних CDN нет.

## Конфигурация

Флаги `go-academy` (каждому есть переменная окружения):

| Флаг | Переменная | По умолчанию |
| --- | --- | --- |
| `--host` | `GOACADEMY_HOST` | `127.0.0.1` |
| `--port` | `GOACADEMY_PORT` | `8080` |
| `--data` | `GOACADEMY_DATA_DIR` | `./data` |
| `--content` | `GOACADEMY_CONTENT_DIR` | `./content` |
| `--frontend` | `GOACADEMY_FRONTEND_DIR` | `./frontend/dist` |
| `--cors` | `GOACADEMY_CORS_ORIGINS` | `http://localhost:5173,http://127.0.0.1:5173` |
| `--go` | `GOACADEMY_GO_BIN` | автопоиск в `PATH`, `GOROOT`, `~/.local/go/bin` |
| `--run-timeout` | `GOACADEMY_RUN_TIMEOUT_SEC` | `10` (секунды, 1–60) |

Обязательные переменные Supabase:

| Переменная | Назначение |
| --- | --- |
| `SUPABASE_DB_URL` (алиас `CONNECTION_URL`) | строка подключения к Postgres (Session pooler) |
| `SUPABASE_ANON_KEY` (алиас `PUBLIC_KEY`) | publishable/anon key для проверки токенов |
| `SUPABASE_URL` | адрес проекта; выводится из `postgres.<ref>` в строке подключения |
| `GOACADEMY_REQUIRE_AUTH` | `1` по умолчанию; `0` отключает проверку токенов для локальной отладки на SQLite |

Frontend читает `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` **на этапе
сборки**. Backend при старте сам читает `.env` из текущего или родительского
каталога; уже заданные переменные окружения имеют приоритет. В production
задавайте значения в панели платформы, а не файлом.

Например, чтобы открыть приложение в контейнере или на другой машине локальной
сети: `--host 0.0.0.0`. CORS нужен только dev-серверу Vite; в собранной версии
достаточно относительных запросов.

## Деплой на Vercel

Проект разворачивается как **два сервиса одного деплоя** (Vercel Services):
статика на Vite и Go-сервер. Конфигурация целиком лежит в `vercel.json` в корне
репозитория; проверяется тестом `backend/internal/deploy/vercel_test.go`.

```json
{
  "services": {
    "backend": {
      "root": "backend",
      "framework": "go",
      "buildCommand": "rm -rf internal/contentfs/assets && mkdir -p internal/contentfs/assets && cp -R ../content/. internal/contentfs/assets/ && go build -tags vercel -o server ./cmd/server"
    },
    "frontend": {
      "root": "frontend",
      "framework": "vite",
      "buildCommand": "npm run build",
      "outputDirectory": "dist",
      "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }]
    }
  },
  "rewrites": [
    { "source": "/api/(.*)", "destination": { "service": "backend" } },
    { "source": "/(.*)", "destination": { "service": "frontend" } }
  ]
}
```

Публичный трафик делится по префиксу: `GET /api/...` уходит в сервис `backend`
с тем же путём (backend и ждёт `/api/...`), всё остальное — в `frontend`, где
несуществующие файлы отдаются как `index.html` (клиентский роутер сам разбирает
`/learning/m03-01`, `/practice` и т. д.).

**Bindings не используются:** сервисы не вызывают друг друга по внутренней сети.
Браузер обращается только к относительному `/api`, поэтому адрес бэкенда нигде не
захардкожен: в dev-режиме его подставляет прокси Vite (`GOACADEMY_API`, при
`vercel dev` — `BACKEND_URL`), в продакшене — правило маршрутизации Vercel.

**Переменные окружения в Vercel.** Задайте их для обоих сервисов:

| Сервис | Переменные |
| --- | --- |
| `backend` | `SUPABASE_DB_URL` (Session pooler), `PUBLIC_KEY` (publishable key) |
| `frontend` | `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` |

`VITE_*` встраиваются в статику на этапе `npm run build`, поэтому после изменения
ключа фронтенд нужно пересобрать. Секреты БД не попадают в клиентский бандл.

Что сделано в коде под serverless:

| Что | Как |
| --- | --- |
| Порт | Платформа задаёт `PORT`; при `VERCEL=1` бэкенд слушает `0.0.0.0:$PORT` (`GOACADEMY_PORT` остаётся приоритетнее) |
| Каталог данных | `$TMPDIR/go-academy` — единственное место, доступное на запись |
| Контент уроков | Команда сборки копирует `content/` в `backend/internal/contentfs/assets`, файл с тегом `vercel` встраивает его в бинарник (`go:embed`), при старте он распаковывается в каталог данных |
| Статика | `--frontend` по умолчанию пуст: HTML и JS раздаёт сервис `frontend`, бэкенд отвечает только за API |
| База данных | Supabase Postgres через `SUPABASE_DB_URL`; SQLite в serverless не используется |

Ограничения платформы, о которых нужно помнить:

- **Холодный старт не теряет прогресс:** пользовательские данные хранятся в
  Supabase, а во временном каталоге лежит только распакованный контент.
- **Нужен сетевой доступ к Supabase.** Используйте Session pooler с IPv4 —
  прямое подключение к `db.<ref>.supabase.co` может не работать из serverless.
- **Запуск Go-кода и проверка решений требуют тулчейна.** Если `go` нет в образе
  сервиса, редактор вернёт понятную ошибку «Go не найден», остальные разделы
  (уроки, карточки, викторины, достижения) продолжат работать.

Локальная проверка сборки сервиса backend ровно так, как её выполнит Vercel:

```bash
cd backend
rm -rf internal/contentfs/assets && mkdir -p internal/contentfs/assets
cp -R ../content/. internal/contentfs/assets/
go build -tags vercel -o server ./cmd/server
VERCEL=1 PORT=3999 ./server     # слушает 0.0.0.0:3999, база — из SUPABASE_DB_URL
```

## Безопасность запуска кода

Код собирается и запускается локально (`backend/internal/runner`):

| Ограничение | Как реализовано |
| --- | --- |
| Временный каталог | `os.MkdirTemp` внутри `data/tmp`, удаляется после запуска |
| Лимит времени | Контекст с таймаутом (`--run-timeout`, по умолчанию 10 с); процесс убивается вместе с потомками |
| Лимит вывода | Не более 256 КБ на поток; при переполнении процесс останавливается, вывод помечается как обрезанный |
| Лимит исходника | 256 КБ кода на запуск |
| Сборка и запуск | Сначала `go build` (ошибки компиляции отделены от выполнения), затем прямой запуск бинарника — без `sh -c` |
| Окружение | `GOPROXY=off`, `GOTOOLCHAIN=local`, `GOWORK=off`, `CGO_ENABLED=0`, общий кеш сборки, `HOME` и `TMPDIR` указывают во временный каталог |
| Очередь | Не более 2 одновременных запусков, остальные ждут свободный слот 15 с и получают понятную ошибку |
| Запрет оболочки | Импорт `os/exec` и `plugin` отклоняется до компиляции: из интерфейса нельзя запустить внешнюю команду |
| Поиск `go` | Проверяется, что найденный файл — настоящий бинарник (ELF/Mach-O/PE), а не скрипт-обёртка |
| Проверка решений | `go test -json` в том же временном каталоге; ожидается отчёт по каждому тесту, иначе решение не засчитывается |

**Важно:** локальный запуск Go-кода **не является полноценной песочницей** — процесс
имеет те же права, что и пользователь, и может читать файлы. Для исполнения
недоверенного кода нужна изоляция: контейнер без сети, с лимитами CPU и памяти,
read-only файловой системой и минимальными правами. Приложение пишет об этом и
в разделе «Редактор», и под редактором в уроке, а не обещает «полную
безопасность».
